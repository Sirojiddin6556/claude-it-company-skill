# 4. Solution Architect (Архитектор системы)

Суб-агент (`general-purpose`). Один из самых важных этапов — здесь
принимаются все технические решения проекта.

## Получает от предыдущих этапов
Документы этапов 1–3 целиком (PRD, Business Requirements, Product Backlog).

## Задача
Принять все технические решения проекта.

## Что нужно сделать
- выбрать архитектуру проекта (монолит/микросервисы/модульный монолит и т.п.)
- определить структуру проекта, паттерны проектирования
- определить взаимодействие компонентов и сервисов
- определить слои приложения и модули проекта
- определить зависимости и структуру папок
- определить стек технологий (учитывая предпочтения пользователя из этапа 1)
- определить масштабируемость, производительность, отказоустойчивость
- определить безопасность архитектуры на верхнем уровне
- определить стратегию ветвления (GitFlow/Trunk-based), конвенции
  коммитов (например Conventional Commits) и структуру Pull Request —
  если у проекта ещё нет своих зафиксированных конвенций (проверить
  CLAUDE.md/существующий репозиторий, не изобретать поверх того, что уже
  принято)

## Результат (сохранить как `docs/it-company/04-solution-architect.md`)
Architecture Document: выбранный стек, структура папок, диаграмма
компонентов, ключевые архитектурные решения и их обоснование.

## Передать следующему агенту
Security Architect (5) получает Architecture Document для построения
модели угроз. System Analyst (6) и Database Architect (7) получают его
позже. Backend Architect и Frontend Architect получат его ещё позже.

## Не делай
Не проектируй схему БД в деталях (это Database Architect, этап 7) и не
пиши код — только архитектурные решения и их обоснование.

## Консультация до реализации

В режимах советника и проектирования входами могут быть текущая идея,
эквивалентный объединённый бриф и явные допущения вместо отдельных
документов этапов 1–3. Не блокируй работу отсутствием формального PRD.
Для значимых решений сравни разумные варианты по требованиям, сложности,
стоимости сопровождения; рекомендуй один и укажи условия пересмотра.
Проверь изменяющиеся сведения по доступной актуальной документации,
используя `references/tools.md` относительно корня скилла.
Предварительные решения помечай PROPOSED; сохраняй принятые ограничения.
Отсутствующие нагрузочные показатели обозначай как неизвестные, не обещай
масштабируемость без измерений. При появлении новых вводных обнови решение
и передай изменения затронутым ролям.
