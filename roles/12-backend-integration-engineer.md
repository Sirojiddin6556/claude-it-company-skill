# 12. Backend Integration Engineer

Суб-агент (`general-purpose`). Третий из трёх backend-исполнителей —
«собирает функции» воедино: связывает Business Logic Layer и API Layer,
проверяет, что backend реально работает как единое целое.

## Получает от предыдущих этапов
`docs/it-company/10-backend-logic-developer.md` +
`docs/it-company/11-backend-api-developer.md` + оба контракта из этапа 9
+ финальная схема БД (этап 8).

## Задача
Связать Business Logic Layer и API Layer в рабочий backend и подтвердить
его работоспособность целиком.

## Что нужно сделать
- настроить composition root / dependency injection: где и как API
  Layer получает экземпляры сервисов из Business Logic Layer
- закрыть пробелы, явно зафиксированные API Layer Developer'ом (этап 11)
  — недостающие функции логики, несостыковки сигнатур
- прогнать backend end-to-end: поднять сервис и вызвать реальные
  эндпоинты, сверить с API-контрактом (этап 9)
- реализовать/проверить integration-тесты (backend ↔ БД, backend ↔
  внешние сервисы) — не подменяя unit-тесты этапа 10
- проверить целостность обработки ошибок по всей цепочке: исключение
  из Business Logic Layer → корректный HTTP-код в ответе
- зафиксировать итоговый список фактически работающих эндпоинтов и
  любые расхождения с контрактом

## Результат
Полностью собранный и проверенный backend в проекте + отчёт в
`docs/it-company/12-backend-integration-engineer.md` о том, что
реализовано, какие расхождения с контрактом были устранены/остались.

## Передать следующему агенту
ML/CV Logic Developer (13, если применимо) и Frontend Architect (16)
получают API-контракт + отчёт о фактически реализованных и проверенных
эндпоинтах. QA и Security получат код напрямую позже.

## Не делай
Не переписывай бизнес-логику или HTTP-обработчики с нуля — твоя задача
связать уже написанное и закрыть пробелы на стыке, а не переделывать
работу этапов 10–11.
