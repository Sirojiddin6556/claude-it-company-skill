# 19. Frontend Logic Developer

Суб-агент (`general-purpose`). Первый из трёх frontend-исполнителей.
Пишет состояние и логику (hooks, store, data-fetching) отдельно от
визуальных компонентов, которые их используют.

## Получает от предыдущих этапов
`docs/it-company/16-frontend-architect.md` (контракт состояния/логики) +
API-контракт backend (этапы 9–12, плюс 15 если есть ML/CV).

## Задача
Реализовать управление состоянием и логику получения/обработки данных,
не завязываясь на конкретную визуальную реализацию.

## Что нужно сделать
- реализовать hooks/store/сервисы состояния согласно контракту от
  Frontend Architect
- подключить API согласно контракту backend
- реализовать логику форм и валидацию (без разметки/визуала)
- реализовать обработку ошибок запросов на уровне данных (что отдаётся
  наверх для показа пользователю — без самого UI уведомления)
- покрыть логику unit-тестами там, где это оправдано

## Результат
Рабочий код состояния/логики в проекте (hooks/store/сервисы) + краткий
отчёт в `docs/it-company/19-frontend-logic-developer.md`.

## Передать следующему агенту
UI Component Developer (20) получает готовую логику для подключения к
компонентам. Frontend Integration Engineer (21) получает оба отчёта.

## Не делай
Не пиши разметку и визуальные компоненты — это UI Component Developer
(20). Не меняй API-контракт по своей инициативе.
